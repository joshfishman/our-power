# Next 15 + NextAuth beta bump — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate Our Power from Next.js 14.2.35 to Next.js 15.x and NextAuth `5.0.0-beta.3` → latest `5.0.0-beta.31`, on two sequential branches so the failure modes stay debuggable.

**Architecture:** Two-phase migration. Phase 1 bumps NextAuth alone, lands on `main` via a PR. Phase 2 — only after Phase 1 is green in production — bumps Next.js with the `@next/codemod` tool plus a manual `fetch()`-caching audit, lands as a separate PR. Direct-to-`main` is explicitly disallowed for both phases; the failure modes (auth broken, every route 500ing on `params`) are too costly without preview-deploy verification.

**Tech Stack:** Next.js 14.2.35 → 15.x · React 18.3 (held, no React 19 in this migration) · NextAuth.js 5.0.0-beta.3 → 5.0.0-beta.31 · @sentry/nextjs 10.38 (works on both Next 14 and 15, no bump needed) · TypeScript 5 · Prisma 7

Expected: usually a handful of errors in files the codemod didn't fully transform — typically because `params` was used inside a helper function rather than destructured at the top of the component.

- [ ] **Step 2: Fix each error in the file the error reports**

Pattern:

```ts
// BEFORE
export default function Page({ params }: { params: { id: string } }) {
  const { id } = params; // ← used directly
}

// AFTER (codemod target)
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
}
```

If the codemod left a function as sync but introduced an `await params`, make the function `async`. If it left `params` typed as `{ id: string }` but a `.then(...)` access slipped through, retype to `Promise<...>`.

After every file fix, re-run typecheck:

```bash

```

Loop until clean.

### Task 8: Audit fetch() caching across `src/app/`

**Files:**

- Possibly modify: any of the 36 `fetch()` callsites in `src/app/`.

- [ ] **Step 1: List the callsites**

Run:

```bash
grep -rn "fetch(" src/app --include="*.ts" --include="*.tsx" > /tmp/fetches.txt
wc -l /tmp/fetches.txt
```

Expected: ~36 lines.

- [ ] **Step 2: Classify each callsite**

Open `/tmp/fetches.txt` and for each line, decide:

- **Did the original code rely on Next 14's auto-caching?** Look at the call site: if it's a server component fetching data with no `cache:` or `next:` option, it was implicitly cached on Next 14. Under Next 15, it's now uncached.
- If the call genuinely wants caching (static data, infrequent change), add `{ cache: 'force-cache' }` as the second arg.
- If the call needs fresh-on-every-request (auth-aware data, user-specific), leave it.

Skip CSR fetches inside `'use client'` components — those weren't affected by Next 14's server-side cache flip.

- [ ] **Step 3: Apply targeted edits**

For each call that needs `force-cache`, edit the call inline:

```ts
// BEFORE
const res = await fetch('https://api.example.com/data');

// AFTER
const res = await fetch('https://api.example.com/data', { cache: 'force-cache' });
```

If `fetch` already has an options object, add `cache: 'force-cache'` to it instead of replacing.
